## Summary
Editing the PAYE statutory item opens **Configure PAYE (Income Tax)** ("Creates a new effective-dated
version"). Saving issues **`PUT /api/v1/payrollApi/statutory-items/1/config`**. The endpoint's band
validation requires each band's `min_income` to be **strictly greater** than the previous band's
`max_income`, but the **seeded PAYE bands are contiguous** (`min_income == previous max_income`), so
**every band fails validation** and the configuration cannot be saved.

## Steps to Reproduce
1. Open Tax & Statutory Configuration → PAYE (Income Tax) → Configure.
2. (Optionally change a rate.) Click **Save Configuration**.
   - Equivalent API: `PUT /statutory-items/1/config` with the seeded `tax_bands` (band1 0–490, band2 490–600, band3 600–730, …).

## Expected
The seeded, contiguous Ghana PAYE bands (band N min = band N−1 max, e.g. 490) save successfully and a
new effective-dated rate version is created (PRD §10).

## Actual — HTTP 422
```
Validation failed:
  Band 2..7: "Min income must be greater than the previous band's max income
             (no overlap at the boundary; e.g. if the previous max is 490, use 491)."
```
So the validator wants `min = prev.max + 1` (e.g. 491 after 490), which contradicts the seeded data
(`min = prev.max = 490`). The PAYE config therefore **cannot be re-saved through its own endpoint**.
(Observed: the UI "Save Configuration" silently does not persist for the default data, consistent with
this 422.)

## Impact
- **PAYE bands/rates cannot be updated via the app** for the seeded configuration (e.g. annual budget
  rate changes) without first restructuring every band boundary to the `+1` convention — which would
  also shift the band math at boundaries (a 1-unit untaxed gap).
- **Blocks a safe round-trip edit:** because the original overlapping boundaries are not re-acceptable
  by the endpoint, an edit **cannot be reverted to the exact original** via the API. Per the QA safety
  requirement (edit then restore exactly), the active band-edit test was therefore **not performed** —
  no bands were changed (verified identical to snapshot `evidence/network/statutory-original-bands.json`).
- Relates to **BUG-001** (the same bands are serialized with inconsistent/zero-width `min_income` on GET).

## Possible Root Cause
The band-boundary validator (`min > prev.max`) is inconsistent with the seeder's boundary convention
(`min = prev.max`). Either the validator should accept `min >= prev.max` (touching boundaries), or the
seed should use the non-overlapping `+1` convention — currently they disagree.

## Suggested Fix
Align the two: relax the validator to allow `min_income == previous max_income` (contiguous bands, the
standard tax-bracket convention), **or** re-seed bands with non-overlapping boundaries. Add a
regression test that opens the seeded PAYE config and saves it unchanged (must succeed).

## Evidence

- `evidence/network/statutory-original-bands.json` (snapshot; bands confirmed unchanged after testing).
