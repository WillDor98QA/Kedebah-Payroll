## Summary
On approved termination run #89 (status = `approved`, not yet paid):
- `POST /pay-runs/89/cancel` → **422**
- `POST /pay-runs/89/reject` → **422**
- `POST /pay-runs/89/return-to-previous` → **422**

So an approved run can **only** move forward to Paid. There is no path to abort/cancel a run that was
approved in error before money is disbursed.

## Expected (per PRD §16)
The lifecycle diagram shows **Reject** (→ draft) and **Return to previous stage** during approval, and
lists **Cancel (with reason)** as an action. A reasonable expectation is that an approved-but-unpaid run
can still be cancelled (aborted) before Mark-as-Paid.

## Actual
All three reverse/abort actions are blocked at the `approved` state; the run is effectively locked to
Mark-as-Paid.

## Caveat / why "needs confirmation"
Reject / Return-to-previous are plausibly intended only for the **pending_approval** stage (this run was
already fully `approved`). The genuinely questionable one is **Cancel** being blocked post-approval.
Confirm intended behaviour with the product owner: is there *any* supported way to void/abort an
approved run before payment?

## Impact
An erroneously-approved run (wrong employees, wrong period, wrong amounts) cannot be stopped except by
paying it. Combined with BUG-006 (over-broad population) this raises the risk of an unintended payment.

## Evidence
- Run #89 (termination, approved): cancel/reject/return-to-previous all 422; left in `approved` state (documented residue).
