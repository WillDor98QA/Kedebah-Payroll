# BUG-012 — Admin-set password at user creation is silently ignored; created users cannot be logged in by the admin

| Field | Value |
|-------|-------|
| **Bug ID** | BUG-012 |
| **Title** | `POST /users` accepts a `password` (and `password_confirmation`) but **silently ignores it** — the new user cannot log in with it (`/login` → "Invalid password"), so an admin cannot provision a working credential at creation time |
| **Type** | IAM / data integrity (silent-accept) |
| **Requirement Ref** | IAM, REQ-AUTH-001 |
| **Test Case Ref** | TC-URB-005, TC-ENT-PW-manager, TC-ENT-PW-reports |
| **PRD Section** | Users & Roles |
| **Module** | Users & Roles / Auth |
| **Severity** | Major |
| **Priority** | P1 |
| **Environment** | https://payroll.kedebah.com → enterprise portal, William & Co Enterprises, Admin, 2026-06-30 |
| **Status** | Open |

## Summary
When creating a user, the API accepts `password`/`password_confirmation` in the payload and returns 200,
but the value is **not applied**. Logging in as the created user with that password fails with
"Invalid password" — identical to a wrong password. The admin therefore cannot hand a new user a working
credential; the user is dependent on an out-of-band activation/reset they may never receive, and (for
QA) two of the four provided accounts (**Manager** `dwetornam@gmail.com`, **Reports** `dwetornam+2@gmail.com`)
now reject **every** known password, leaving them un-loginable.

## Steps to Reproduce
1. `POST /users { user_data: { …, password: "X", password_confirmation: "X" } }` → 200, user created.
2. Log in as that user with password "X" → **"Invalid password"** (auth rejects it).
3. The accept-and-ignore is silent: no warning that the password was not set.

## Expected
Either honour the admin-set password at creation, **or** reject the field with a clear error and provide
an explicit admin "set / reset password" (or invite/activation) path that results in a usable credential.

## Actual
Password is silently dropped; created users cannot be logged in by the admin. Accounts can drift into an
unknown-password state (Manager/Reports reject both temp and reset values).

## Impact
**Major — onboarding is broken / opaque.** Admins believe they set a password; they did not. Combined
with BUG-011 (no module access), a "created" user is effectively unusable, and there is no reliable
admin-driven way to give them a working login.

## Suggested Fix
Honour `password` at create (hash + store) or return a validation error and expose a real admin
set/reset-password endpoint; surface the activation state in the user record.
