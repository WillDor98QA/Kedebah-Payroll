# BUG-010 — Employee payment_method create/update rejects the snake_case values the API itself returns

## Summary
Creating/updating an employee requires `payment_method` in **Title Case** ("Cash" succeeds; `cash` →
422 "The selected payment method is invalid"). But `GET /employees` **returns** `payment_method` as
**snake_case** (`cash`, `bank_transfer`, `mobile_money`). So a client that reads an employee and submits
it back unchanged is **rejected** — the accepted enum ≠ the emitted enum.

## Steps to Reproduce
1. `POST /employees … payment_method:"cash"` → **422**.
2. `POST /employees … payment_method:"Cash"` → **201**.
3. `GET /employees/{id}` → `payment_method:"cash"` (the value just created is echoed lowercase).

## Expected
Accept and emit the same canonical value (accept snake_case, or return Title Case) so round-trip
create→read→update works.

## Impact
Low — round-trip edits / integrations break unless the client re-maps the casing; confusing for API
consumers. (Workaround: send Title-Case labels on write.)

## Suggested Fix
Normalise `payment_method` to one canonical representation on both validation (accept) and serialization
(return), or accept both casings.

## Evidence
Employees sweep: `payment_method:"cash"` → 422; `"Cash"` → 201; GET echoes `cash`.
