# BUG-009 — Invalid/tampered Bearer token returns HTTP 500 instead of 401 Unauthorized

| Field | Value |
|-------|-------|
| **Bug ID** | BUG-009 |
| **Title** | **Any** auth failure — tampered/invalid token **AND a missing token entirely** — causes **HTTP 500** (unhandled error) rather than **401 Unauthorized** |
| **Type** | Security robustness / error handling |
| **Requirement Ref** | REQ-SEC-003 (session validation) |
| **Test Case Ref** | TC-SEC-005 |
| **PRD Section** | §2 |
| **Module** | SEC |
| **Severity** | Medium |
| **Priority** | P3 |
| **Environment** | https://payroll.kedebah.com (sandbox), William & Co Enterprises, 2026-06-26 |
| **Status** | Open |

## Summary
Calling a protected endpoint with a malformed/tampered Bearer token (e.g. `Bearer 99999|deadbeeftampered|<tenant>`)
returns **HTTP 500 "An unexpected error occurred"** instead of a clean **401 Unauthorized**. Invalid
authentication should be rejected deterministically with 401, not raise a server error.

## Steps to Reproduce
1. `GET /banks?per_page=1` with `Authorization: Bearer 99999|deadbeeftampered|<tenant>` → **500**.
2. `GET /employees?per_page=1` with **no `Authorization` header at all** (only `Accept: application/json` + `X-Requested-With`) → **500** (re-confirmed 2026-06-26).

Both the *invalid-token* and the *no-token* paths 500 — i.e. the API **never returns a clean 401** for an unauthenticated request; the auth middleware throws instead of rejecting.

## Expected
**401 Unauthorized** (token invalid/expired) with no stack/exception surface.

## Actual
**500 Internal Server Error** — suggests an unhandled exception while parsing/validating the token.

## Impact
- Incorrect status code breaks client auth-refresh logic (clients key off 401 to re-authenticate).
- 500s on auth input are a robustness/security smell (potential information disclosure; auth code path throws on attacker-controlled input).

## Notes (related security results — all PASS)
- SQL injection in inputs → stored literally, no injection (banks table intact).
- Malformed/wrong-type input → 422 (graceful).
- Cross-tenant: a bogus `X-Tenant-Id` is **ignored** (token's embedded tenant governs) → no cross-tenant data leak. ✅
- Stored XSS: API persists `<script>` raw (no server-side sanitisation) — defense relies on the
  frontend escaping on render (Vue escapes `{{ }}` by default). Recommend confirming all bank/employee
  name renders + the xlsx/PDF exports escape user input. (Tracked as an observation.)

## Suggested Fix
Catch token-decode/validation failures in the auth middleware and return 401 (with a generic message).
