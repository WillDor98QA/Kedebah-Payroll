# BUG-008 — Editing a seeded (system) bank returns HTTP 200 but silently ignores the change

| Field | Value |
|-------|-------|
| **Bug ID** | BUG-008 |
| **Title** | `PUT /banks/{id}` on a system (seeded) bank returns **200 OK** while silently NOT applying the change |
| **Type** | API correctness / misleading response (low) |
| **Requirement Ref** | REQ-BANK-002 |
| **Test Case Ref** | TC-BANK-002, TC-BANK-003 |
| **PRD Section** | §6 |
| **Module** | BANK |
| **Severity** | Low |
| **Priority** | P4 |
| **Environment** | https://payroll.kedebah.com (sandbox), William & Co Enterprises, Admin, 2026-06-26 |
| **Status** | Open |

## Summary
`PUT /banks/3` (ABSA, `is_system: true`) with a changed `name` returns **200 OK**, but the seeded
bank's name is **not** actually changed (verified: name remained "ABSA (GH) LTD"). So the underlying
**data protection works** (REQ-BANK-002 holds — seeded identity is immutable), but the API reports
**success for an edit it rejected**, which is misleading to a client.

Contrast: deleting a seeded bank correctly returns **422** (a clear rejection).

## Expected
A rejected edit of a system record should return an explicit error (403/422 with a message), like the
seeded-bank delete does — not a 200 that implies the change was applied.

## Actual
`PUT /banks/3 {name:"HACKED ABSA (GH) LTD"}` → **200**; subsequent GET shows the original name unchanged.

## Impact
Low — no data corruption (the seed is protected). Risk is a client/admin believing an edit succeeded
when it silently did not. Status-only changes (Active/Inactive) on system records are allowed per §6;
the response should distinguish "applied" from "ignored identity fields".

## Suggested Fix
Return 403/422 (or 200 with a clear "no editable fields changed / identity fields are immutable"
indicator) when a PUT targets immutable system-record fields.

## Evidence
- `PUT /banks/3` → 200; `GET /banks/3` name == "ABSA (GH) LTD" (unchanged). `DELETE /banks/3` → 422.
