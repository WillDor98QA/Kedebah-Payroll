# BUG-005 — Statutory config "Save Configuration" silently fails: UI sends POST to a PUT-only endpoint

| Field | Value |
|-------|-------|
| **Bug ID** | BUG-005 |
| **Title** | Statutory item config save uses `POST /statutory-items/{id}/config` but the route only accepts **PUT** → HTTP 405 → no statutory config change persists via the UI |
| **Type** | Functional defect (frontend HTTP method) |
| **Requirement Ref** | REQ-TAX-001, REQ-TAX-003 (configure statutory items / dated rate versions), PRD §1 (data-driven config) |
| **Test Case Ref** | TC-TAX-005 |
| **PRD Section** | §10 |
| **Module** | TAX |
| **Severity** | High |
| **Priority** | P1 |
| **Environment** | https://payroll.kedebah.com (sandbox), business "William & Co Enterprises", Admin, 2026-06-25 |
| **Status** | Open |

## Summary
The **Configure (statutory item) → Save Configuration** action issues
**`POST /api/v1/payrollApi/statutory-items/{id}/config`**, but that route is **PUT-only**. The POST
returns **HTTP 405** ("The POST method is not supported … Supported methods: GET, HEAD, PUT"), so the
save **silently fails and no configuration change is persisted**. This affects **all** statutory items
(observed on PAYE id 1 and Tier 1 id 2).

## Steps to Reproduce
1. Settings → Tax & Statutory Configuration → any item (e.g. Tier 1) → Configure.
2. Change a value (e.g. employee rate 5.5 → 5.6), set an effective date + reason → **Save Configuration**.
3. Reopen the item / GET `/statutory-items` → the value is **unchanged**.

## Expected
The change saves and a new effective-dated rate version is created (PRD §10).

## Actual
- Captured request: `POST /statutory-items/{id}/config` → **405**.
- The same payload via **`PUT /statutory-items/{id}/config`** returns **200** and persists correctly
  (proven: editing Tier 1 EE 5.5→6 via PUT then reprocessing run #79 recomputed Tier1 EE 165→180,
  exactly matching the oracle; restoring via PUT returned the rate to 5.5 and the value to 165).

## Impact
- **Statutory configuration cannot be updated through the application UI** — PAYE bands, Tier/SSNIT
  rates, etc. cannot be changed by an administrator (e.g. for an annual budget rate change). The
  engine itself **is** data-driven and honours config changes when applied via the correct method
  (PUT) — so this is purely a frontend HTTP-method defect, but it disables a core admin capability.
- Compounds with **BUG-004** (band-overlap validation), which independently blocks PAYE band saves.

## Possible Root Cause
Frontend uses `POST` (or a misconfigured method) for the config-save call; the API route is registered
as `PUT` only.

## Suggested Fix
Change the frontend save to **`PUT`** (or add a `POST` alias / method-override on the route). Add an
e2e regression test that edits a statutory rate via the UI and asserts the change persists.

## Evidence
- Captured UI requests (PAYE, Tier 1): `POST …/config`.
- API method check: `POST …/config → 405`; `PUT …/config → 200` (with persistence).
- `evidence/network/tier1-original.json` (snapshot; Tier 1 verified restored to 5.5/8/13.5).
