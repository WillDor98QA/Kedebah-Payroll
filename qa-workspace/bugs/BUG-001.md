# BUG-001 — PAYE band `min_income` serialized incorrectly in /statutory-items (cosmetic; calc correct)

| Field | Value |
|-------|-------|
| **Bug ID** | BUG-001 |
| **Title** | PAYE statutory-item bands 3 & 4 return `min_income == max_income` (zero-width brackets) in the config API |
| **Type** | Data hygiene / API serialization — **NOT a calculation defect** |
| **Requirement Ref** | REQ-TAX-002, REQ-PAYE-008 |
| **Test Case Ref** | TC-TAX-001, TC-PAYE-008 |
| **PRD Section** | §10, §24 |
| **Module** | TAX |
| **Severity** | Low |
| **Priority** | P3 |

| **Status** | Open |

## Preconditions
Authenticated admin in a Ghana-seeded business.

## Steps to Reproduce
1. `GET /api/v1/payrollApi/statutory-items?paginate=false&country_id=84`.
2. Inspect the PAYE (Income Tax) item's `bands` array.

## Expected Behaviour (per PRD §24)
Contiguous monthly brackets: 0–490 (0%), 490–600 (5%), **600–730 (10%)**, **730–3,896.67 (17.5%)**,
3,896.67–19,896.67 (25%), 19,896.67–50,416.67 (30%), 50,416.67+ (35%). Each band's `min_income`
should equal the previous band's `max_income`.

## Actual Behaviour
Bands 3 and 4 return collapsed (zero-width) ranges:
```
band 3 (10%):   min_income = 730       max_income = 730        ← should be 600 → 730
band 4 (17.5%): min_income = 3896.67   max_income = 3896.67    ← should be 730 → 3896.67
```
This leaves apparent gaps for chargeable income in 600–730 and 730–3,896.67 in the **config payload**.
(`cumulative_tax` values on every band are correct: 0, 5.5, 18.5, 572.67, 4572.67, 13728.67.)

## Impact assessment — verified, NOT affecting tax
The **engine computes PAYE correctly**. The per-employee `calculation_breakdown.paye_band_trace`
(live run #80) uses the correct boundaries:
```
0–490 @0% =0 · 490–600 @5% =5.5 · 600–730 @10% =13 · 730–3896.67 @17.5% =554.17 · 3896.67+ @25% =258.33
chargeable_income 4930 → PAYE 831
```
Independent oracle `paye(4930) = 831.00` — **exact match**. The live PAYE-vs-oracle spec passes for
every processed employee in run #80. So the band `min_income` issue is **serialization/seed data
only**, with no effect on computed tax. Severity therefore **Low**.

## Evidence
- `../evidence/network/statutory-items.json` (raw bands)
- `../evidence/network/run-80-employees-full.json` (correct `paye_band_trace`)
- Passing spec: `automation/tests/payroll/seed-and-paye.live.spec.ts`

## Possible Root Cause
Seed/serializer sets each band's `min_income` to its own `max_income` (or the boundary lookup uses
`cumulative_tax` + previous `max_income`, leaving `min_income` unused and mis-seeded).

## Suggested Fix
Set each band's `min_income` to the previous band's `max_income` (600 and 730 respectively) so the
config API is self-consistent and won't mislead any downstream consumer that reads `min_income`.
